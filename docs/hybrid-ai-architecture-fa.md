# معماری ترکیبی هوش مصنوعی و مسیریابی تسک‌ها

**هدف جدید محصول:** دستیار ویندوزیِ محلی‌محور که درخواست‌ها را به طرح‌های چندمرحله‌ایِ قابل‌اعتبارسنجی تبدیل کند. کار سبک روی دستگاه انجام شود؛ کار سنگین، در صورت انتخاب کاربر، بتواند از ارائه‌دهندهٔ هوش مصنوعی بیرونی استفاده کند.

این سند هدف معماری را ثبت می‌کند، نه ادعای قابلیت‌های پیاده‌سازی‌شده. وضعیت فعلی پایین همین سند و در README مشخص شده است.

## ۱. دو مسیر اجرا

### محلی — پیش‌فرض و آفلاین

- مدل محلی و دسته‌بند فعلی روی دستگاه اجرا می‌شوند؛ در این حالت هیچ درخواست هوش مصنوعی به اینترنت نمی‌رود.
- پیش از بارگذاری مدل، حافظهٔ آزاد، سقف حافظهٔ مجاز، تعداد رشتهٔ CPU، سقف مصرف CPU و زمان تخمینی بررسی می‌شود.
- آداپتور مدل باید مصرف را حین اجرا نیز محدود کند، اولویت فرایند را پایین نگه دارد و لغو/timeout را پشتیبانی کند. بررسی پیش از اجرا به‌تنهایی سقف سخت‌افزاری محسوب نمی‌شود.
- اگر برآورد نشان دهد مدل از بودجه فراتر می‌رود یا حافظهٔ ذخیرهٔ امن سیستم باقی نمی‌ماند، مدل محلی بارگذاری نمی‌شود.

### ترکیبی — محلی‌محور با امکان سرویس بیرونی

- کار سبک ابتدا به مدل محلی سپرده می‌شود.
- برای کار سنگین یا خیلی سنگین، برنامه می‌تواند ارائه‌دهندهٔ بیرونیِ پیکربندی‌شده را پیشنهاد دهد.
- **ارسال بیرونی خودکار و پنهانی نیست:** پیش از هر تسک، نام سرویس/مدل، داده‌ای که ارسال می‌شود و بازهٔ زمان تقریبی نمایش داده می‌شود. تنها پس از موافقت همان تسک درخواست ارسال می‌شود.
- در صورت رد ارسال، کاربر می‌تواند تخمین محلی را ببیند و اگر در بودجه جا می‌شود آن مسیر را برگزیند؛ وگرنه برنامه تسک را اجرا نمی‌کند.
- حالت «فقط محلی» حتی در صورت فعال‌بودن ارائه‌دهنده هیچ‌گاه به مسیر بیرونی fallback نمی‌کند.

## ۲. زمان تقریبی تسک

زمان به‌صورت بازهٔ **سریع / معمول / کند** همراه با میزان اطمینان نمایش داده می‌شود، نه یک وعدهٔ قطعی. پایهٔ برآورد باید داده‌های اندازه‌گیری‌شدهٔ محلی باشد:

- برای مدل محلی: زمان بارگذاری/گرم‌شدن، سرعت ورودی و خروجی مدل روی همان دستگاه، اندازهٔ درخواست و حد CPU انتخاب‌شده.
- برای API: تأخیر و زمان پاسخ همان ارائه‌دهنده و مدل، به‌همراه اندازهٔ درخواست؛ شبکه متغیر است، پس بازه و اطمینان باید محافظه‌کارانه باشد.
- برای کارهای فایل: شمار و حجم فایل‌ها و throughput اندازه‌گیری‌شده.
- اگر نمونهٔ کافی برای برآورد وجود ندارد، باید «برآورد اولیه/اطمینان پایین» نشان داده شود؛ نباید عدد دقیقی جعل یا تاریخچه به بیرون ارسال شود.

اندازه‌گیری‌های عملکرد فقط در دستگاه ذخیره می‌شوند و قابل پاک‌کردن‌اند. هیچ telemetry یا تاریخچهٔ حاوی مسیر/محتوای کاربر برای تخمین لازم نیست.

## ۳. شناسایی سخت‌افزار و بودجهٔ منابع

Probe فعلی Windows اطلاعاتی را که از رابط‌های استاندارد سیستم قابل‌خواندن است جمع می‌کند: نام و فرکانس گزارش‌شدهٔ CPU، تعداد هسته‌های فیزیکی و پردازنده‌های منطقی، RAM کل/آزاد، ظرفیت و فضای خالی volumeهای ثابت، وضعیت برق AC/باتری و درصد باتری. اگر خواندن تعداد هسته‌های فیزیکی در دستگاهی ممکن نباشد، مقدار «نامشخص» می‌ماند.

منبع برق، توان PSU را گزارش نمی‌کند؛ Windows به‌شکل عمومی دما، توان مصرفی دقیق، سلامت خنک‌کاری یا wattage منبع تغذیه را در همهٔ دستگاه‌ها عرضه نمی‌کند. GPU در MVP استفاده نمی‌شود و GPU/دما/PSU اگر از رابط استاندارد قابل‌دسترسی نباشند «نامشخص» می‌مانند؛ نباید با حدس پر شوند. به همین دلیل هیچ نرم‌افزاری نمی‌تواند از آسیب فیزیکی برای هر سیستم تضمین بدهد؛ کنترل این پروژه سقف مصرف خودِ عامل و حفظ headroom برای سیستم‌عامل است.

`ResourceGovernor` سقف‌های **اولیه و محافظه‌کارانهٔ عامل** را بر اساس سخت‌افزار و بار لحظه‌ای محاسبه می‌کند:

- CPU عامل: حداکثر ۳۵٪ روی AC، ۲۰٪ روی باتری و ۱۵٪ در وضعیت برق نامشخص؛ با حفظ headroom پردازنده و توقف شروع کار وقتی مصرف کلی CPU به ۸۰٪ برسد.
- حافظهٔ مدل: حداکثر کمینهٔ ۱ گیگابایت و ۲۰٪ RAM کل، و در هر حال کمتر از RAM آزاد پس از ذخیرهٔ حداقل ۱ گیگابایت یا ۳۰٪ RAM برای بقیهٔ سیستم.
- I/O دیسک: سقف آغازین ۱۰ MiB/s روی AC، ۳ MiB/s روی باتری و ۲ MiB/s در وضعیت نامشخص؛ در نبود volume ثابت با فضای آزاد بیش از ۱ GiB سقف نوشتن صفر است.
- تعداد رشتهٔ محلی حداکثر ۲ است و GPU در MVP خاموش می‌ماند. روی باتری سقف شدت کلی عامل نیز حداکثر ۶۰٪ و در برق نامشخص حداکثر ۴۰٪ است.

این اعداد سقف مصرف **فرایند عامل** هستند، نه آستانهٔ ایمنی/دمای تضمین‌شدهٔ سخت‌افزار. آن‌ها باید روی دستگاه واقعی benchmark و در صورت نیاز سخت‌گیرانه‌تر شوند. بودجهٔ دستی نمی‌تواند از سقف سخت عبور کند. میکس اولویت پیش‌فرض ۴۰٪ CPU، ۴۰٪ RAM و ۲۰٪ دیسک است؛ وقتی کاربر سهم یکی را تغییر می‌دهد، سهم‌های دیگر خودکار بازتوزیع می‌شوند و جمع همیشه ۱۰۰٪ می‌ماند. شدت کلی نیز جداگانه قابل انتخاب است، ولی سقف شدتِ وابسته به برق/بار سیستم قابل‌دورزدن نیست.

پنل منابع در UI وجود دارد و تنظیمات شدت/سهم‌ها در فایل محلی ذخیره می‌شوند؛ probe در شروع، هر ۳۰ ثانیه و بلافاصله پیش از کپی تازه می‌شود. کپی فایل سقف ثابت ۱۰ MiB/s دارد و از سقف governor (AC/باتری/نامشخص: ۱۰/۳/۲ MiB/s) پیروی می‌کند؛ پیش‌نمایش و اجرا نیز reserve یک GiB فضای مقصد را نگه می‌دارند. با این حال CPU/RAM فعلاً فقط در preflight محاسبه می‌شوند: limiter حین اجرای مدل، Job Object و runtime مدل محلی هنوز وجود ندارند. سنجش لحظه‌ای پیش از اجرا به‌تنهایی enforce محسوب نمی‌شود؛ تا runtime محدودشده پیاده‌سازی نشده، نباید مدعی شد که مصرف CPU/RAM حین اجرا به‌طور قطعی کنترل شده است.

## ۴. زیرساخت اتصال به ارائه‌دهنده‌های بیرونی

کد هسته به قرارداد `IAiPlanningProvider` و رجیستری ارائه‌دهنده‌ها وابسته است، نه به یک API خاص. برای هر اتصال واقعی، آداپتور جداگانه لازم است تا قالب درخواست/پاسخ، محدودیت context، احراز هویت، timeout، retry و خطاهای نرخ/سهمیه را مدیریت کند.

- رابط باید امکان افزودن سرویس‌های شناخته‌شده و مدل‌های رایگان/دارای سهمیهٔ رایگان را بدهد؛ رایگان‌بودن، سقف سهمیه و دسترس‌پذیری سرویس‌ها تغییر می‌کند و نباید در برنامه تضمین دائمی شود.
- هزینهٔ قابل‌پرداخت پیش‌فرض باید صفر باشد. پیش از تسک، نام مدل و هرگونه محدودیت یا هزینهٔ احتمالی نمایش داده شود؛ بدون تنظیم و اجازهٔ کاربر سراغ مدل پولی نرویم.
- کلید API هرگز در گفتگو، prompt، history، فایل تنظیمات plaintext یا log قرار نمی‌گیرد؛ در پیاده‌سازی Windows باید از Credential Manager/DPAPI استفاده شود.
- درخواست خارجی به‌طور پیش‌فرض فقط شامل متن لازم برای طرح‌ریزی و فهرست مهارت‌های مجاز است. مسیرهای فایل، محتوای فایل، تاریخچه و اطلاعات شخصی ارسال نمی‌شوند مگر کاربر همان داده را جداگانه انتخاب و تأیید کند.
- اتصال provider فقط وقتی فعال است که کاربر Hybrid را انتخاب کرده و provider را تنظیم کرده باشد. هیچ API در کد پایه یا تست‌ها خودکار فراخوانی نمی‌شود.

## ۵. مرز اختیار مدل و ایمنی اجرا

مدل محلی یا بیرونی فقط **پیشنهاد طرح ساختاریافته** تولید می‌کند. مدل فرمان، PowerShell، کد، executable یا عملیات مستقیم UI اجرا نمی‌کند.

چرخهٔ اجرای تسک:

```text
درخواست
  → تشخیص نیاز و پیچیدگی
  → پیشنهاد طرح از مدل انتخاب‌شده
  → اعتبارسنجی schema و همهٔ شناسه‌های skill با فهرست محلی
  → پیش‌نمایش گام‌ها، منابع، دادهٔ ارسالی و ETA
  → تأیید کاربر (و تأیید جداگانه برای ارسال بیرونی/عمل پرخطر)
  → اجرای مهارت‌های ثبت‌شده با checkpoint، timeout و لغو
  → بررسی نتیجه و ثبت خلاصهٔ محلی
```

درخواست خارج از مهارت‌های ثبت‌شده به کار غیرمجاز تبدیل نمی‌شود؛ دستیار باید توضیح دهد کدام قابلیت را ندارد. هیچ مدل یا provider نباید امکان افزودن skill دلخواه در زمان اجرا را برای خودش داشته باشد.

محدودیت‌های فعلی همچنان برقرارند: حذف، جابه‌جایی، بازنویسی فایل و اجرای فرمان/مسیر دلخواه در MVP فعال نیستند. هدف عمومی‌تر به‌تنهایی مجوز اجرای این عملیات پرخطر نیست؛ هر تغییر در این مرزها نیازمند تصمیم و طراحی جداگانه است.

## ۶. کارهای تکراری و تسک‌های پیچیده

کارهای تکراری باید به‌صورت workflow قابل‌مشاهده و قابل‌ویرایش از همان skillهای مجاز ساخته شوند؛ تعریف workflow کد یا فرمان دلخواه نیست. در فاز نخست، اجرای دوباره دستی و نمایش پیش‌نمایش کافی است. زمان‌بندی خودکار فقط بعد از پشتیبانی از توقف، انقضا، مدیریت خطا و کنترل روشن کاربر اضافه شود.

تسک پیچیده به چند گام محدود تقسیم می‌شود؛ پیش‌شرط و نتیجهٔ موردانتظار هر گام مشخص است. اجرای گام بعدی به اعتبارسنجی نتیجهٔ گام قبل وابسته است و شکست/ابهام باید اجرای باقی گام‌ها را متوقف کند.

«هر درخواست» هدف توسعهٔ پوشش مهارت‌هاست، نه وعدهٔ اجرای هر عمل ممکن. برای افزودن یک حوزهٔ جدید (مثلاً برنامهٔ جدید یا یک گردش‌کار تکراری)، باید skill مشخص، قرارداد ورودی/خروجی، policy، پیش‌نمایش و آزمون آن به‌صورت مستقل ساخته شود.

## ۷. نقشهٔ پیاده‌سازی

1. **قرارداد و policy:** حالت Local/Hybrid، برآورد منابع، بازهٔ ETA، تصمیم مسیریابی و شرط رضایت برای هر ارسال بیرونی. این گام در Core شروع شده است.
2. **سنجش Windows:** دریافت RAM/CPU واقعی، بودجهٔ قابل‌تنظیم و اجرای محدودشده؛ جمع‌آوری زمان‌های محلی بدون telemetry.
3. **مدل محلی:** انتخاب runtime و مدل کوچک پس از benchmark فارسی/کیفیت/RAM؛ بارگذاری تنبل، توقف‌پذیر و تحت سقف مصرف.
4. **اتصال بیرونی:** انتخاب providerهای مشخص، پیاده‌سازی adapter، نگهداری امن کلید، quota/cost guard و تأیید ارسال در UI.
5. **اعتبارسنج و گردش‌کار:** schema/skill validator و اجرای چندمرحله‌ایِ قابل‌توقف.
6. **UI Automation:** پشتیبانی محدود و آزمون‌شده برای برنامه‌های هدف؛ فقط کنترل‌های معنایی UIA و فقط actionهای ثبت‌شده.
7. **تخمین و پایش کیفیت:** نمایش بازهٔ زمان و اطمینان، مقایسه با زمان واقعی و تنظیم محلی تخمین‌ها.

## ۸. وضعیت فعلی کد

- مدل فعلی فقط دسته‌بند محلی سبک است؛ مدل زبانی مولد محلی هنوز نصب یا اجرا نمی‌شود.
- قرارداد provider/ETA و `AiRoutingPolicy` در Core تعریف شده‌اند؛ probe سخت‌افزاری Windows برای CPU/RAM/volumeها/AC و باتری، `ResourceGovernor` با سقف سخت/بازتوزیع سهم‌ها، پنل تنظیمات و ذخیرهٔ محلی preferences اضافه شده‌اند. snapshot هنگام شروع، هر ۳۰ ثانیه و بلافاصله پیش از کپی تازه می‌شود. پیش‌نمایش کپی ذخیرهٔ دیسک را بررسی می‌کند و اجرای کپی با سقف I/O انجام می‌شود.
- سقف‌های CPU/RAM هنوز در runtime واقعی enforce نمی‌شوند؛ فقط پیش‌شرط منابع برای شروع بررسی می‌شود و کپی دیسک را محدود می‌کند. limiter حین اجرای مدل، Job Object، اتصال provider به UI، اتصال API، مدل مولد محلی، ETA کالیبره‌شده و UI Automation هنوز وجود ندارند. آداپتر Windows Credential Manager اضافه شده اما به provider وصل نیست.
- تست‌های policy/governor نوشته شده‌اند، اما به علت نبود .NET SDK اجرا نشده‌اند. GPU، دما و wattage منبع تغذیه در probe عمومی فعلی نامشخص می‌مانند؛ سقف‌های اولیه محافظه‌کارانه‌اند و تضمین جلوگیری از آسیب فیزیکی نیستند.
- بنابراین فعلاً هیچ درخواست کاربر به سرویس بیرونی ارسال نمی‌شود و این کد هنوز ادعای انجام عمومی تسک‌ها را ندارد.
